# Unicode Normalization (`EC-FS-004`)

`nfc/café.md` — `caf` + U+00E9 (single codepoint), `63 61 66 c3 a9 2e 6d 64` — is the only file here. This directory originally held an NFD sibling for `EC-FS-005` as well; it was removed. Two findings, in the order they were hit:

**Finding 1 — same-directory collision, worked around.** Writing NFC and NFD forms of "café" into the *same* directory did not produce two directory entries on this authoring host (macOS, APFS, default normalization-insensitive-but-preserving mode). The second write's normalization-insensitive lookup matched the first write's entry and silently **overwrote its content**. No error, no warning — this is the exact failure `EC-FS-004`/`EC-FS-005` exist to catch, happening to the corpus itself. Splitting the two forms into separate sibling directories (`nfc/`, `nfd/`) was verified to avoid this: each directory's normalization-insensitive lookup is independent, so distinct byte sequences survive as distinct entries.

**Finding 2 — commit-time precomposition, not worked around.** That fix held for the *working tree*, but not for git. This repository's `core.precomposeunicode` is `true` — git's own filesystem auto-detection at clone/init time on macOS/APFS, not a setting anyone chose. With it set, `git add`, and even plumbing-level `git update-index --cacheinfo`, both silently rewrite an NFD path to NFC before it reaches the object database. Verified directly: a working-tree file confirmed byte-for-byte NFD via `os.listdir` showed up as NFC bytes in `git ls-files -z` after staging, with **no error**. This corrupts the committed path *at commit time, on this host* — it does not depend on which platform later clones the repository. An NFD file committed from a Mac with this git default can never test NFD, anywhere, once committed.

**Consequence:** `EC-FS-005` cannot be a *committed* corpus case under this constraint. It moves to `EC-FS-X-006` in the generator-only set, materialized at test time in a temporary directory on a host/config where it survives — the same category `EC-FS-X-001` (case collision) already occupies, for the same underlying reason: a normalization- or case-insensitive layer silently collapsing two distinct byte sequences into one. See `docs/testing/test-vault-spec.md §5.6`.

**For anyone touching this directory:** never write NFC and NFD forms of the same basename into the same directory on a normalization-insensitive filesystem. And do not assume `git add` preserves NFD bytes on macOS — verify with `git ls-files -z | python3 -c "..."` (byte-level, not terminal display) before trusting it.
